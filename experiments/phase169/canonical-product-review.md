## Which compiler each executable contains

Let `S` be unchanged canonical Phase152 source and `E` be the frozen experimental
native source `df8d6475…`, with streaming Phase168 entry and publication provenance.

| Construction | Executable's algorithm when subsequently run |
|---|---|
| Qualified Phase152 compiles `E` → experimental N1 | New experimental entry/algorithm, generated by the qualified old backend |
| Experimental N1 compiles `S` → this canonical product | **Original canonical entry/algorithm**, generated by the new backend |
| Experimental N1 compiles `E` → experimental N2 | New experimental entry/algorithm, generated by the new backend |

The canonical product does not contain the publication optimization merely
because its producer used that optimization while checking `S`. The source
being compiled determines the resulting algorithm. Likewise its main is the
canonical multi-command QBE main, not `p169n_args`. Native stage labels in the
receipts record construction lineage; they do not change these source facts.

This makes the canonical product useful for a clean generated-code experiment:
on the same `S` and exact cache/source identity, correct execution should emit
the original118,227,421-byte QBE oracle. On `E`, it should reproduce the original
Phase169 N1 acquisition QBE under the same input identity/policy. The latter
tests the experimental source as an input to the old algorithm; it does not
promote this product into an experimental successor. The qualified old compiler
already admitted `E`, so there is no new source-language feature required.

Only the actual experimental N2 applies the new algorithm while enjoying its
own generated code. Its self-emission must compare against N1's emitted `E`
product, and its canonical request against the94,447,397-byte product here.
These are semantic/self-hosting gates still requiring execution, not conclusions
from this census. In particular, feeding `S` to the canonical product should
**not** be required to reproduce its own94MB acquisition stream: it contains
the old emitter.

## Remaining opportunity large enough to save over20 seconds

First measure experimental N2 rather than immediately adding another pass.
The197.355s producer was itself generated by the old backend. A further24%
complete execution reduction would meet150s, but the static evidence does not
establish that reduction. This next generation is the cheapest direct test of
whether the new representation helps its own implementation.

The largest remaining structural exposure is the **44,295 scheduled functions,
including37,607 continuation-named bodies, occupying73.575MB—77.9% of all QBE**.
Large persistent-update and verifier/body computations still retain their
scheduled forms; direct imports did not solve general non-tail result
construction. Another cache or another scalar predicate is too narrow to remove
this inventory and its construction/analysis/destruction.

The next general change would retain one recursive computation with explicit
resumable constructor frames, so the original and direct/region paths no longer
construct and rediscover equivalent continuation bodies separately. Test complete
persistent index update with retained old roots plus a recursive verifier/tree
consumer; the [Phase167 obstruction graph](../phase167/admission-obstructions.md)
already identifies `index_remove`, insertion and body/schema SCCs. Keep actual
fallback demand, source ownership, bounded stack and final verification. This
does not authorize dropping every scheduled function or adding unrestricted C
recursion.

The prior full diagnostic's registry16.190s plus rendering/output/teardown40.208s
is a56.398s **historical envelope**, before accounting for candidate production
and optimization. A40% reduction in that complete pair would save22.56 diagnostic
seconds. That gives a concrete >20s falsifiable target, **not a forecast for the
new197s build**: its stage profile has not yet been measured, and not every
remaining segment is redundant. Retain numeric identities and compact frame
facts from their producer; Phase148 already falsified packing and unpacking an
extra temporary IR around unchanged consumers.

If experimental N2 is slower, use the same canonical product comparison to
separate generated-code regression from new-algorithm construction savings
before broadening this change. That is a much wider and better-grounded decision
than another tiny cache, equality replacement or metadata-count optimization.
