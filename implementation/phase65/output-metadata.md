# Phase65: ordered-body demand metadata

**Status: neither candidate admitted work on the four latency sources; no build retained.** Source
inspection uses baseline `49431ba`; Phase64's closed evidence is untouched.
No live compiler edit, compiler/Node target or Git operation was performed in
this lane's preparation.

The direct backend already has the important structured layer: `JDTextLeaf`
carries exact use/reference notes, size and scanner-safety state, and
`JDTextJoin` combines children without scanning their strings again. Replacing
that layer or adding another output IR would duplicate existing machinery.

The narrower remaining repetition is in `jd_ordered_bindings`. Once an ordered
parallel-let body has been emitted, each binder independently searches the same
`prefix ++ value` string for its exact `JD_USE` marker. The
[isolated patch](../../selfhost/tools/performance/phase65/output-metadata/candidate.patch)
uses one existing `jd_text_raw` leaf for groups with at least two binders and
shares `jd_text_used` queries. It preserves zero/single-binder searches and the
public String-taking helper. `JDOrdered` and `JDText` layouts do not change.

This is a bounded first discriminator, not complete metadata propagation across
all expressions. It still scans once at that String boundary and the later
final-output path remains unchanged. The compiler grows **27 Bend lines and
three helpers**, with no new datatype. The tradeoff must earn its maintenance
cost through whole-request measurements.

## Semantics and falsifier

`jd_use(id)` includes a physical newline and the exact decimal `U32.show(id)`.
On a safe leaf, the existing scanner recognizes exactly that form; leading-zero
IDs and prefix-similar IDs remain distinct. Unsafe or over-limit text invokes
the same old substring search over the complete original string. The candidate
parses the joined body as one leaf, avoiding a new cross-chunk marker rule.
Reference notes are collected by the existing scanner but do not themselves
trigger reachability admission during local demand selection.

Names, quotation, generated bytes, binder slots, fresh temporary numbers and
the original binding join are unchanged. A demanded live RHS still derives its
type and emits in the original order; erased demanded RHSs remain `null`, and
unused RHSs remain unvisited. A faster wrong-demand decision is a rejection.

The correctness owner reviewed this equivalence and found no source blocker,
conditional on the unchanged single-leaf parser/fallback boundary. The
[control proposal](../../selfhost/tools/performance/phase65/output-metadata/README.md)
requires exact complete enclosing values, raw/module equality, marker/refusal
edges and explicit demand/order observations before clean performance work.
Writing or reviewing those controls is not a passing execution result.

The performance risk is substantial: old searches can stop early, whereas the
shared leaf scans the whole body and allocates notes. Two binders may still be
too few to amortize that work. The initial threshold is fixed before timing.
Fresh selected-B2 profiles and actual admission counts must establish a useful
opportunity; no 2–6% planning range is claimed as an observed or assured gain.
Negligible admission or flat/regressed complete-request time should stop this
candidate rather than motivate a broader representation rewrite by default.

The fresh four-source ancestry survey attributes 4/10/11/10 exact CPU samples
to `jd_text_scan` under `jd_text_raw` on Numeric/Lexer/Map/Raytrace, respectively.
The admitted timestamp weights are about 5/33/32/31 ms. It found no exact
`jd_ordered_bindings` frame; inlining or shared dispatch means absence does not
prove zero work. This narrower proposal must not claim all of the raw scanner's
sampled cost as its opportunity.

Root therefore requested an opportunity census **before any candidate build**.
The [observer](../../selfhost/tools/performance/phase65/output-metadata/opportunity.mjs)
binds the actual original genuine B2, counts multi-binder groups and haystack
positions visited by their actual old substring searches, and requires exact
original complete modules on all four sources. It records lexical edits and
verifies their inverse, preserves original prepared-cache identity admission,
and uses a private ordinary-driver import without an injected API override.
All counters are diagnostic; they are neither clean clocks nor estimates of
the cost of the unbuilt candidate.

## Source-only follow-up: preserve nested closure bodies

A different boundary still renders structured output and immediately scans it
again. `jd_closure` calls `jd_body`, which renders `jd_doc_body`; the
no-argument live-lambda arm of `jd_doc_body_live_lambda` wraps that String in
`return …;` and calls `jd_text_raw`. Its caller already establishes a lambda
with a normalized, non-erased function type. That arm can instead compose the
existing `jd_doc_body` result between compiler-owned literal leaves
`return jd_clo(($arg)=>{` and `});`, preserving `jd_without_owner(env)`,
`wnf(book, ty)` and the initial `"$arg"` argument. This changes no datatype or
String API and needs no additional helper or source line.

The [isolated one-line patch](../../selfhost/tools/performance/phase65/output-metadata/closure-candidate.patch)
and [receipt](../../selfhost/tools/performance/phase65/output-metadata/closure-candidate.json)
are unapplied. Correctness source review found no blocker under the enclosing
production-call preconditions; arbitrary direct calls outside those preconditions
are not a claimed contract. This is a next hypothesis, not a measured result or
retained patch. Validate actual admission and nested body sizes first. Correctness must
compare complete emitted bytes and USE/REF/refusal behavior rather than equal
JDText tree shape, because the intended change retains joins instead of one
rescanned leaf. The literal boundary sizes are exactly 23 and 3 code points;
neither literal adds a newline or marker. Existing raw/foreign leaves keep
their scanner and fallback. Erased-lambda handling remains in its preceding
branch. This opportunity is separate from the zero-admission ordered-bindings
candidate above.

P65-006 is [registered separately](../../experiments/phase65/P65-006-structured-closure-return.md).
The first original-B2 census attempt refused before compilation because the
generated live-lambda function is a dispatcher entry wrapper: the raw call is
in `jd_doc_body$scc` state 2, not in that wrapper. The failed raw report at

and consumed controller remain preserved. The corrected
[second observer](../../selfhost/tools/performance/phase65/output-metadata/closure-opportunity02.mjs)
checks the wrapper's state ordinal and instruments that exact dispatcher state

The [focused controller](../../selfhost/tools/performance/phase65/output-metadata/closure-compare.mjs)
is source-reviewed and binds the candidate patch/manifest and the checked
snapshot's exact changed `core.bend` hash; unchanged baseline code cannot pass

semantics and full modules against the old route, with optional cap controls
required before retention. New nested-capture and erased-inner-lambda witnesses
have source-level expected results 15 and 17, respectively; execution and
