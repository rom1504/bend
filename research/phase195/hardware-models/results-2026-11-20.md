## Authentication, method and rejected first attempt

Downloaded the pinned official Debian archive using approved network access.
Verified exact8,463,020-byte size and SHA256
`1dd51ffbda01aa2440dca7336d11a8b1410655151ccaf9fbe135c6f41e0d947a`
before extracting only `./usr/lib/llvm-11/bin/llvm-mca` into the workspace.
[Acquisition receipt](evidence/acquisition.json) pins the archive, binary and16
resolved library/loader files, including existing LLVM11. Dynamic dependency
inspection found no libpfm requirement. No package installation or system
configuration change occurred; package archive and tool remain under
`selfhost/build/phase195/hardware-tool01` as active reproducibility dependencies.

The first ten-call attempt exposed an important validation failure: LLVM11 emits
an **error on stderr but exits0** for objdump's direct `jmpq label` spelling,
then models the remaining instructions. It omitted one branch per iteration
from every input. Its runner's initial `complete:true` field and successful
guard therefore do not qualify the predictions. That attempt is explicitly
rejected; its untouched [raw report](evidence/run01/report.json), outputs and
[runner snapshot](evidence/run-retrospective-rejected-v1.py) are retained.

The corrected [runner](run-retrospective.py) preserves original inputs and writes
separate model inputs with exactly one spelling normalization `jmpq`→`jmp`.
No instruction is removed. It requires exit0, empty stderr and exactly
`100 × selected instruction count`. All ten corrected calls satisfy these
checks. [Accepted report](evidence/run02/report.json) retains exact argv, both
input pins, all verified binaries/receipts, tool/library pins, timings and stdout/
stderr identities. Complete copied outputs sit beside it. Each call uses
`-mtriple=x86_64-unknown-linux-gnu -mcpu=ivybridge -iterations=100`, with
`-noalias=true` for eight base inputs and `false` for pressure-many only.
Each process has a2s timeout; the entire guarded job has a30s limit.

## Cost, limits and disposition

The accepted ten model processes consumed0.360s elapsed and0.339s child CPU;
its guard consumed1.189s and sampled94.86MiB peak process-tree RSS. Including
the rejected attempt, guards consumed2.238s total and20 model processes0.674s
elapsed/0.627s CPU. The accepted declared-root peak allocation was192KiB,
under a16MiB budget with the default5GiB disk reserve. Acquisition archive/tool
storage and report-copy/archive work are outside those model guard costs.
Each job ran on CPU2, allowed by host affinity0–7, in a coordinated shared-lock
gap; no compiler timing target overlapped. Agent effort/billing was unavailable.

Both runs are sealed through maintained retention: first `rejected`, second
`completed`, with verified archives under
`selfhost/build-retention/phase195-hardware-mca01` and `...mca02`; no pruning.
The initial closure command used the wrong output namespace and was refused;
a later overlapping close request was refused by the shared lock. Correct
sequential closure completed; neither refusal executed target work.

These are straight-line positive-path projections with rewritten symbolic branch
targets, not original layout. LLVM-MCA repeats that sequence and uses scheduling
models; the model cannot recover omitted dynamic paths or measured frontend
effects. Cache hierarchy and store-to-load forwarding are not modeled, and
default no-alias assumptions are not a program proof. The model's default
register/load/store capacities and the old LLVM11 scheduling data further limit
absolute claims. See the [LLVM11 documentation](https://releases.llvm.org/11.0.0/docs/CommandGuide/llvm-mca.html).
Actual layout, branch prediction, memory stalls, call/runtime work and missing
profile weights prevent conversion to end-to-end performance. Identical kernel
bytes support backend neutrality; they do not prove layout caused the observed
runtime differences.

Use these results to prioritize removable work and to recognize abstentions.
Paired measured runtime remains the performance authority. A prospective,
profile-connected candidate is the next useful validation, separately declared
before seeing its runtime outcome; no compiler promotion follows from this report.
