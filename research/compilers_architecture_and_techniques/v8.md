# V8: architecture, optimization techniques, and the Bend JavaScript boundary

Research date: **2026-10-04**. This is source research, not a benchmark campaign.
The coherent source pin is V8 **13.8.258.18**, commit
[`a14ab029e21658cba458b7001281c5d526e67636`](https://chromium.googlesource.com/v8/v8/+/a14ab029e21658cba458b7001281c5d526e67636),
committed **2025-06-17**. This historical revision is reproducible;
it is not asserted to be the latest V8 or the exact V8 embedded in our Node executable.
Official articles explain design intent; pinned implementation resolves pipeline details.
Public source files were fetched from the V8 GitHub mirror at this exact commit.
Selected functions and their surrounding implementation were inspected, rather than
inferring mechanisms solely from blog descriptions or filenames.
No compiler source, installed release, benchmark or historical evidence was changed.

## What V8 contributes after Bend emits JavaScript

Bend emits JavaScript; V8 parses and executes that JavaScript, not Bend terms or `JW`.
V8 sees actual objects, properties, functions, arithmetic, control flow and effects.
It does not receive Bend's affine quantities, dependent types or private-graph proof.
Therefore two different optimization problems meet at the emitted-program boundary.
Bend can erase proved descriptor/application protocols before runtime execution.
V8 can specialize the resulting JS operations for observed shapes and types.
These mechanisms compose; a generic dispatcher does not automatically disappear
merely because a powerful optimizing JIT consumes it.
The comparison baseline is installed worker23's [IR guide](../../selfhost/docs/JAVASCRIPT_IR.md).
That guide describes two cooperating non-SSA IRs, not a fully unified backend.

## Tier architecture and source entry points

The conceptual tiers are JavaScript parsing, Ignition bytecode/interpreter,
Sparkplug baseline code, Maglev optimizing code, and peak optimizing compilation.
Tiering is a policy decision; each function need not execute every tier in order.
The pinned implementation also contains a flag-selected Maglev-to-Turboshaft frontend.
Turboshaft is compiler infrastructure/IR, not an additional execution tier after TurboFan.
The historical [Ignition/TurboFan launch](https://v8.dev/blog/launching-ignition-and-turbofan)
explains bytecode's role as both executable baseline and optimizing-compiler input.

### Parsing and Ignition

`Parser::ParseProgram` initializes scanning, reconstructs scope context and parses
the program into function-literal structure. `ParseFunctionLiteral` chooses
preparsing according to lazy eligibility and possible background work.
This avoids fully compiling every shipped function during startup.
The [official preparser article](https://v8.dev/blog/preparser) explains why skipping
an AST still requires scope/variable information, including captured variables.
It is not permission to skip syntax checks or JavaScript lexical semantics.

`BytecodeGenerator::GenerateBytecode` establishes the execution/result scope,
allocates top-level registers, initializes required contexts and emits the body.
Call/property generation uses feedback slots, including `AddCallICSlot`
and `AddLoadICSlot`; later compilation can consume observed execution information.
Ignition's bytecode and frame layout give optimized execution a baseline to resume.
For Bend, smaller generated functions can reduce parse/bytecode work before any JIT win.
This is an architectural inference; no startup savings were measured in this study.

### Sparkplug: inexpensive baseline compilation

`BaselineCompiler::GenerateCode` has a preparatory bytecode walk followed by
`VisitSingleBytecode` code emission. The pinned source therefore retains two walks.
The [Sparkplug article](https://v8.dev/blog/sparkplug) describes the broader design:
compile bytecode directly, use interpreter-compatible frames, and reuse builtins.
It deliberately avoids a general optimizing IR and its compilation overhead.
Do not transfer the article's browser benchmark gains to Bend workloads.
Sparkplug removes interpreter dispatch costs; it does not prove that Bend's own
`apply`/matcher/continuation protocol has become unnecessary.

### Maglev: feedback-driven SSA with bounded compilation work

The [Maglev design](https://v8.dev/blog/maglev) describes bytecode prepass/liveness,
forward graph construction, loop phis, representation specialization and deopt state.
The pinned `MaglevCompiler::Compile` calls `MaglevGraphBuilder::Build`, then
flag-selected non-eager inlining, loop optimization and phi representation selection.
It follows with use/dead-node processing and register-allocation/codegen preparation.
Thus the design's emphasis on graph-building reductions does not mean literally one pass.

In [maglev-graph-builder.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/maglev/maglev-graph-builder.cc),
`BuildCheckMaps` merges known map information and checks compatibility.
A constant object with a matching stable map can register `DependOnStableMap`.
Already sufficient known-map information avoids a repeated runtime map check.
Contradictory map/type information can emit `kWrongMap` deoptimization.
This is stronger evidence than assuming every property read always checks its shape.
It is also weaker than claiming every generated-object shape check disappears.

### TurboFan and Turboshaft: separate stages, compatible responsibilities

`PipelineImpl::CreateGraph` builds from bytecode and applies the inlining phase.
`OptimizeTurbofanGraph` trims, types and lowers; its configured sequence includes
loop handling, load elimination, escape analysis and simplified lowering.
The sequence is flag-sensitive; not every build executes every optional phase.
The [original TurboFan design](https://v8.dev/blog/turbofan-jit) explains reducers
and layered lowering through a sea-of-nodes graph; that article is historical.

The pinned Turboshaft `Pipeline` supports `CreateGraphFromTurbofan` and
`CreateGraphWithMaglev`, then `OptimizeTurboshaftGraph` and native generation.
The latter includes machine lowering, optional unrolling/store elimination,
`OptimizePhase`, optional typed optimization and code elimination/simplification.
This is a concrete coexistence of frontends, not evidence that the pin has
universally removed TurboFan's JS graph frontend.
The inspected [optimize-phase.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/turboshaft/optimize-phase.cc)
composes structural, late-escape, pretenuring, memory, machine and value-numbering
reducers in a copying phase. This is a concrete reducer schedule, not just a list
of optimizations inferred from available files.
[machine-lowering-phase.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/turboshaft/machine-lowering-phase.cc)
similarly composes string-escape, JS generic, DataView, machine and fast-API
lowering with select/machine/value-numbering reducers.
[code-elimination-and-simplification-phase.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/turboshaft/code-elimination-and-simplification-phase.cc)
orders dead-code/stack-check work, load-store simplification, duplication
optimization and instruction-selection normalization; ordering is part of the contract.
`BuiltinPipeline::OptimizeBuiltin` has its own CSA phases; those must not be
mistaken for an unconditional user-JavaScript pass list.

## Escape, allocation and reconstruction

There are several distinct allocation optimizations, with different proof boundaries.
The inspected [escape-analysis-reducer.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/escape-analysis-reducer.cc)
uses analysis results to replace operations and relax allocation effects for
virtual objects that have not escaped. `ReduceDeoptState` traverses frame state,
describes virtual object fields and deduplicates repeated virtual-object identities.
Removing a physical allocation therefore requires a recoverable logical object,
not just deleting an object literal because its type appears immutable.
The paired [escape-analysis.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/escape-analysis.cc)
implements the analysis whose results the reducer consumes.

The later [late-escape-analysis-reducer.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/turboshaft/late-escape-analysis-reducer.cc)
has a narrower job: `CollectUsesAndAllocations`, `AllocationIsEscaping`,
`EscapesThroughUse` and `MarkToRemove` remove allocations used only as
destinations of initialization stores, together with those stores.
Removing a store can make a nested allocated value dead, so the worklist revisits it.
This is dead-allocation elimination, not a universal heap-to-stack conversion.
It does not imply that a returned tree, identity-observable object or arbitrary
recursive structure becomes allocation-free.

[memory-optimization-reducer.h](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/turboshaft/memory-optimization-reducer.h)
separately contains `MemoryAnalyzer::AllocationFolding`, allocation lowering,
and write-barrier elimination based on allocation/value facts.
Allocation folding can share allocation reservation while preserving separate objects.
It must not be reported as eliminating those logical objects or their observable identity.
`SkipWriteBarrier` distinguishes young allocation state and values needing barriers.
Consequently an allocation profile and a count of object-literal syntax measure
different things; neither alone identifies which V8 optimization happened.

For Bend, removing the private field array reduces a concrete representation layer.
Whether V8 later scalar-replaces a temporary object depends on visible uses,
inlining, effects and required deopt state. This is a conditional inference.
V8 cannot be assumed to scalar-replace an entire recursively returned data graph.
Bend also cannot remove materialized intermediates without its own alias/demand proof.

## Load elimination, aliases and effects

[late-load-elimination-reducer.h](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/turboshaft/late-load-elimination-reducer.h)
defines `LateLoadEliminationAnalyzer` with alias, map and memory-content snapshots.
It tracks facts at blocks and merges predecessor snapshots; redundant loads may
be replaced with a prior load or stored value when intervening effects permit it.
The reducer also handles a checked tagged-load/truncation-to-int32 pattern.
This is representation-sensitive memory reasoning, beyond lexical copy propagation.
Existence of this reducer does not establish that every JS tier/front-end invokes it;
the inspected TurboFan frontend separately schedules its own load-elimination phase.

The matching [implementation](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/turboshaft/late-load-elimination-reducer.cc)
is explicit in `ProcessCall`: calls without write effects preserve memory state.
Some recognized builtins have targeted invalidation or fresh-object treatment.
Other writing calls invalidate non-alias information for inputs and potentially
aliasing memory. Knowing a source-level helper name is not enough to retain loads.
This explains why exposing a small direct callee can improve optimization opportunity;
it does not establish that V8 treats every direct call as pure.

Bend's ordinary `JIRGlobal` can observe computed demand, mutation, getters or
errors. `JWGlobal` retains a global load under its narrower literal-global
admission and entry proof; computed private nullary references instead become
explicit `JWDirectCall` instructions. Neither node name supplies a reusable-load permission.
Private layout projections are a better candidate only inside their proved boundary.
A future Bend load-elimination pass would need explicit effects, alias facts,
branch joins and invalidation; the current lexical facts environment is insufficient.
This is a possible transfer of analysis structure, not an authorized implementation.

## Representations and arithmetic

[representations.h](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/turboshaft/representations.h)
distinguishes register representations such as tagged, word32/64 and float32/64,
and separate memory representations for loads/stores.
Representation is not interchangeable with a JavaScript-language type.
Word operations, boxed values, compressed pointers and floating values require
different conversions, checks and GC treatment.
`SimplifiedLoweringPhase` occurs after typing/escape phases in the inspected frontend;
its representation/truncation work cannot simply reuse arbitrary high-level types.

Worker23's Number-Nat pass has a different responsibility: prove a whole graph
can use exact Number arithmetic in `0..2^48-1`, preserve overflow/division rules,
and convert at the public BigInt boundary. V8 optimizes the resulting Number JS.
It does not infer that the original BigInt program may generally become Number.
Similarly, emitted modulo-U32 operations must retain their intended semantics;
a feedback-derived Smi range is not a replacement for Bend's range contract.
Avoid attributing a backend representation improvement to V8's tagging alone.

## Inlining, feedback and profitability

[js-inlining-heuristic.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/compiler/js-inlining-heuristic.cc)
contains `CollectFunctions`, `JSInliningHeuristic::Reduce` and `Finalize`.
It identifies candidate functions, checks eligibility and observed call frequency,
inlines qualifying small functions promptly, and budgets larger candidates.
`Finalize` reserves budget for smaller functions exposed by an earlier inline.
Absolute/cumulative bytecode-size limits and polymorphic candidate handling
make unrestricted source expansion an unreliable optimization strategy.
This is the inspected TurboFan heuristic; Maglev has a separate inlining mechanism.

`TieringManager::ShouldOptimize` distinguishes Maglev eligibility, failed compilation,
profile-guided cached decisions, optimization filters and resource modes.
It refuses peak optimization for excessively large bytecode functions.
`InterruptBudgetFor` includes bytecode length and invocation thresholds.
These are explicit costs/policy gates, not proof that one fixed warmup count suffices.
Do not transplant threshold numbers across engine releases or architectures.

Direct lexical worker calls can expose a stable target and reduce dispatcher layers.
Small shared helpers can allow V8 to inline useful work under its budgets.
Large repeated branch bodies, generic fallback duplication and continuation switches
can increase bytecode/compile pressure; a smaller source is not automatically faster.
Inlining benefit depends on caller hotness, feedback, callee size and downstream effects.
These are mechanistic hypotheses requiring actual emitted-code measurements.

## Shapes, private objects and arrays

The [official property-model article](https://v8.dev/blog/fast-properties) explains
hidden classes, construction-order transitions, named fields and indexed elements.
Stable construction shape can support field-offset specialization and inline caches.
Packed/holey and numeric/object elements are separate array representation concerns.
Two objects sharing a shape do not thereby have identical tags, values or identity.

Worker23's `{$:tag,_0:field,...}` layout removes the public `a` field-array layer.
Consistent property order plausibly improves shape predictability and direct access.
The older `{$:tag,a:[...]}` layout can also have a stable outer shape;
it adds array access and allocation rather than necessarily being megamorphic.
Conversely, per-constructor named layouts may introduce multiple maps at a shared site.
Assess the actual field site and constructor cohort instead of assuming either
all tags are monomorphic or every tag is a separate V8 map.
Deleting properties, hostile accessors and public mutation retain JS semantics.
Private ownership permits Bend to avoid some of those protocols before V8 sees them.

## Deoptimization is not Bend's ordinary fallback

[deoptimizer.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/src/deoptimizer/deoptimizer.cc)
contains `ComputeOutputFrames`, `DoComputeUnoptimizedFrame` and
`MaterializeHeapObjects`. Optimized execution can reconstruct baseline frames
and logical values after a speculative assumption fails or dependencies invalidate.
Inlined frames and eliminated objects require recovery metadata.
This is continuation of the same JavaScript computation at an appropriate state.

Bend's guarded public entry instead selects a proved private route or ordinary route.
If the guard refuses, ordinary runtime semantics execute from their established entry.
It does not reconstruct an Ignition frame from partially executed `JW` instructions.
Likewise the 32-native-entry budget transfers recursive work to a private continuation
machine preserving its current private representation; it is not JIT deoptimization.
Calling either mechanism deopt would hide different proof and recovery obligations.

## Tests and evidence discipline

[escape-analysis.js](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/test/mjsunit/compiler/escape-analysis.js)
contains optimized/unoptimized execution checks for joins, loads/stores and loops,
with optimization preparation and forced optimization in the engine test harness.
[late-load-elimination-reducer-unittest.cc](https://github.com/v8/v8/blob/a14ab029e21658cba458b7001281c5d526e67636/test/unittests/compiler/turboshaft/late-load-elimination-reducer-unittest.cc)
checks `Int32TruncatedLoad_Foldable` and refusal when additional uses require tagging.
These demonstrate complementary semantic and IR-structure tests; none were run here.

Transfer the testing pattern: assert complete results and required refusal cases,
then separately inspect the actual transformed graph/emitted worker.
Keep allocation, CPU attribution, clean timing and compiler cost as distinct evidence.
Existing [Phase45 results](../../implementation/phase45/results.md) report a maintained
45-point/23-source corpus and its qualification limits; they are prior measurements.
This document supplies no new timing, allocation estimate or V8 pass attribution.
In particular, a measured Bend gain under Node does not show which V8 tier/pass caused it.

## Practical comparison with the private `JW` pipeline

| Concern | V8 source evidence | Bend worker23 boundary |
| --- | --- | --- |
| Facts | Feedback, map/type checks, dependencies and effect/alias state | Checked whole first-order graph and exact native provenance. |
| IR | Bytecode, Maglev CFG/SSA, TurboFan and Turboshaft graphs | Explicit ordered `JWDirectCall`, assignments, cases and returns; non-SSA. |
| Calls | Heuristic inlining and speculative target specialization | Proved target indices, complete SCCs and direct private calls. |
| Objects | Shapes, escape analysis, virtual-object recovery and allocation lowering | Private named fields/native constructors; public ABI stays explicit. |
| Recursion | JS native execution and engine frame/deopt machinery | Tail loops, shared native-entry budget and private continuation machine. |
| Refusal | Compilation bailout or runtime speculative deoptimization | Admission refusal/entry guard fallback without frame reconstruction. |
| Cost | Tiering, hotness and bytecode/inlining budgets | Measured root profitability and compiler-request costs, still incomplete. |

The highest-confidence implication is to preserve explicit target/layout/representation
facts through Bend's IR and emit compact, ordinary JavaScript for V8 to optimize.
Do not duplicate a speculative JIT merely to repeat its machine-level work.
Potential additions—escape/effect facts, bounded shared analyses and profitability—
need Bend-specific proof boundaries and independent falsifiers before implementation.
Record exact Node/V8 identities when testing these ideas; this research pin alone
does not identify the engine configuration that executed any historical Bend sample.
