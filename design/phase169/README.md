# Phase169 — target a complete native self-build below 150 seconds

Start: `4a47e78`, branch `selfhost/bootstrap`. The user requests substantial
implementation work toward a complete native self-build in **150s or less**.
The retained Phase152 full-build observation is249.222s on3,085,157 source bytes;
reaching150s requires about39.8% less wall time. This is a target, not a forecast.

## Comparable objective and current evidence

Measure fresh source-to-executable construction, including actual source checking,
backend work, independent final verification, all output, QBE, assembly and linking.
Use the same source, prepared-Base policy, runtime/toolchain and resource lane per
comparison. Keep emission/QBE overlap distinct from additive stage CPU clocks.
Source extraction is not a speedup unless its changed contract is stated.

The Phase168 route is experimentally useful on verifier/lookup computations:
12%/40% less complete hosted build time, roughly unchanged/+7% generated runtime.
Native full-scale compatibility, cost and self-reproduction remain unmeasured.
The current best hypothesis combines less backend work with cheaper execution of
the compiler itself; generic omission alone has only a4.83% diagnostic envelope.

## Ordered execution and decision gates

1. Recover bounded disk headroom from exact archived, superseded intermediates.
   Keep qualified images, active work, source/API snapshots and independent oracles.
2. Expose the final Phase168 verified import-before-discovery route through the
   existing native request protocol. Stream from the maintained cursor rather
   than first materializing a full compiler's textual output. Compare collected
   hosted bytes to Phase168 before scaling; preserve private/public/borrowed gates.
3. Transfer to a larger real checker/optimizer closure. Require complete independent
   outputs and bounded runtime/memory. A source checker accepting an unsafe
   declaration is not a mathematical proof; unsupported paths do not count.
4. Acquire one experimental native image using the qualified Phase152 producer.
   Test its exact emitted products against independent hosted outputs on small
   controls, then compile the same canonical full source used by the baseline.
   Separately test its own experimental source and self-reproduction; a smaller
   self source must not be compared to the249s reference as a same-input gain.
5. In parallel with source work, inspect retained profiles for a general native
   execution improvement. Constructor/take/ownership boundaries are an evidence-
   backed candidate. Use exact fallback/alias/stack contracts and a cheap complete
   kernel test before acquiring a new full compiler. Reject narrow low ceilings.
6. Reuse previously validated publication provenance only if the integration is
   small and its real invariant survives. Credit it as existing work, and preserve
   complete output equality for preparation-only changes.
7. Measure the promising integrated full path. If≤150s is reached, repeat under
   matched conditions and qualify N1/N2 plus independent semantic/runtime gates
   before considering promotion. If it is not reached, continue from the measured
   remaining cost rather than claiming a smaller source or emission-only success.

## Resource and validation discipline

One root-owned target execution lane on CPU3; bounded agents handle independent
source, machine-shape, critical-path and retention tasks. All target jobs use the
maintained guard, explicit whole-run disk budget, default5GiB reserve and bounded
RSS/time. No overlapping full builds, broad campaign without a successful small
test, or repeated full qualification after documentation-only changes.

Keep Phase152 and installed selection unchanged until new qualification justifies
promotion. Preserve negative attempts, source/tool identities and exact complete
output evidence. Record target execution cost separately from implementation and
agent effort. No new backend, unsafe verifier bypass, benchmark-name recognizer,
unchecked source route or silent runtime/memory-policy change is authorized by
the performance target.

## Ambitious extensions, conditional on evidence

The practical plan is to combine already demonstrated semantic-interface reuse
with an execution improvement large enough to close the remaining gap. A broader
extension is one durable verified preparation boundary, retaining typed callable,
ownership and continuation facts across selection without duplicate bodies.
A much larger extension would replace the primary control representation with
ordinary direct regions and explicit resumable frames. Neither extension is
mandatory: first establish its whole-request ceiling and cheapest falsifier.
