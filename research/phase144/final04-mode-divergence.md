# Final04 ordinary/session output divergence

The failed first final04 batch smoke exposed **different optimization policies in
two entry paths**, not an established JavaScript/native semantic mismatch. The
source-level diagnosis is corroborated by exact ordinary-mode product checks
and an independently generated hosted session oracle.

## Evidence and source trace

The frozen final04 source is 2,999,209 bytes, SHA-256
`865cff6a02da261952cac824bed0fe91882e60f1c6e4062fbe57f5804745c4ed`.
Its three overrides are documented in
[the composition design](../../design/phase144/final04-composition.md).
One makes `p114s_ranges(boundary)` return `boundary`: ordinary lowering no longer
runs that optional outer range pass. It does not change the separately cached
range pass used by the session backend.

| Entry path | Relevant source call chain | Outer range policy |
| --- | --- | --- |
| Ordinary checked source | `p134e_plan` → `p128raw_session_finish` → `p114s_ranges_lowered` → `p114s_ranges` | Identity in final04 |
| Batch/session | `p140n_compile` → `p140n_cached` → `p140b_session` → `p140b_opened` → `p134u_optimize` → `p134u_inlined` → `p134u_committed` → `p134u_ranges` | Still runs, including from empty state |

`p134u_range_inner` invokes `p113k_function` for an empty or mismatched memo.
`p134u_committed` invokes `p134u_ranges` unconditionally on the valid optimized
boundary. Neither calls `p114s_ranges`. This is distinct from range work inside
the inliner, which remains in both modes.

The failed batch's first decoded product is 577,297 bytes, SHA-256
`d7f319ddfe98e211951e305d692fa0190f4c2ade7cf0beb998a5e88ae7f13559`.
It equals final03 ordinary lexer output. Final04 ordinary hosted lexer is
577,601 bytes, SHA-256
`7020b75d6122405f5bd728a5eee4553183d92184447f4e3213dd16afd62e57ce`.
The retained 116-line diff is localized around the lexer function: the batch
product propagates literals 10, 48 and 0 into copies, stores and tests, removes
two `extuw` operations and renumbers local values/blocks. No static-data/header
changes were observed. This is the predicted shape of the retained outer range
optimization. It is not a general correctness proof of the new constructor
existence analysis.

Local raw evidence is under `selfhost/build/phase144/`:

- `final04-host-smokes01-batch/report.json`: preserved failed exact comparison,
  SHA `6bb170a5f1d8e705f2b37a4fe986298790d7f6e2fd72c9ce56231476a479321b`.
- `final04-smoke-diff01/`: diagnostic decode and diff. Decoding without an
  expected product was diagnostic only; it did not convert the failed gate into
  a passing gate or supply a new oracle.
- `final04-ordinary-mode-equality01.json`: independent offline join,
  SHA `63d33ee628de983c6175de310f1be3764f9be648bf15d8930b55cb9b0345f174`.

The native ordinary suite used the historical prepared-Base carrier; hosted

## Independent session check

The [new hosted session oracle](../../selfhost/tools/performance/phase144/native/session-mode-oracle-v02.mjs)
uses the unchanged checked Bend session implementation from the same final04
source, exposed through an additional checked API. It retains the original
API04 identity as the source-plan authority and separately authenticates the
extra exports and upstream-checker input closure.

For the successful request path it invokes `p140s_named`, `p140g_prepare`, then
`p140r_begin_cursor`/`p140r_next`, matching the native computation. It obtains
independent cold session products A and B from separate empty states, then
requires hosted A/B/A/B to equal those products exactly. The native batch and
session smokes must subsequently equal those independently generated bytes.
No native decoded product is an oracle input. Cache reuse reconstructs complete
text, with checked prior-piece ordinals; the byte comparison is not relaxed to
semantic or normalized equivalence.

Source review of that orchestration passed. Failed-request rollback behavior is
not established by this valid-request sequence. Execution and qualification
remain separate gates owned by the coordinating agent.

The coordinating agent subsequently executed that oracle: all six hosted
observations passed in `final04-session-oracle02/report.json`. Independently
generated cold A is exactly the 577,297-byte `d7f319dd…f13559` product observed in
the original native batch diagnostic; cold B is also 577,297 bytes, SHA-256
`a2e4c548b86fb1a3b7915d24eb6934315a9752e944f39e19df01e0b4814b48e8`.
Hosted seed/edit/revert/edit-again each exactly equal their corresponding cold
product. This validates the predicted mode distinction without taking native
bytes as expected output.

The first oracle preflight stopped before importing the API because two generated
checker snapshots had different directory paths. Version 2 permits relocation of
exactly `method.py` and `stage0-library.mjs` between the old/new API directories,
requires identical bytes/hash and input count, retains exact paths for all other
inputs, and verifies both old and new snapshot pins. The original failed
preflight remains evidence. No compilation or oracle-computation rule changed.

The mode-specific smoke and sealer use a shared authenticated oracle contract,
require the separate ordinary-three receipt, and retain the first failed smoke.
Independent source review caught stale `aa`/`br` references in the unconsumed
`seal-v04.py`; `seal-v05.py` instead obtains exact revision source pins from the
authenticated mode report. That successor preserves all native/provider gates
and explicitly records the cross-mode and incremental-qualification limits.

The coordinating agent then completed the native mode-specific gates in
`final04-host-smokes02/report.json` (SHA
`6fd9282a2bbfdc5e4b9d80ed29ac158b9c92ea098008c53ea407e1c7f0d793c8`):
both provider gates, all four batch products and both session products passed.
The final raw qualification is `final04-qualification.json`, SHA
`a5c48ec98d18a23b91d676ce4052cc7fa5c82bb5169e85d92873411a3d338168`.
It binds these finite smokes, the ordinary-three equality receipt, both focused
native suites, ordinary45 and complete Q2/Q3 reproduction. It explicitly retains
`incrementalQualified=false` and `crossModeByteIdentityClaimed=false`. No failed
receipt was replaced and no compiler rebuild was needed for policy alignment.

## Boundary that remains

The original Phase140 screen required cached output to equal **ordinary**
output, as well as cold-session output. Final04 no longer has that cross-mode
byte identity. A correct per-mode oracle does not restore it. Reports must keep
`incrementalQualified=false`, preserve the failed original smoke and qualified
final03 fallback, and explicitly state the mode-specific policy. No compiler
rebuild is needed to diagnose or test this distinction. A later policy
consolidation should decide whether cross-mode byte identity is again required,
rather than silently assuming that independently implemented pass schedules
stay aligned.
