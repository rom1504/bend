# The ambitious speed agenda

These are the architectural opportunities we care about. The objective is to
make useful Bend applications faster than upstream where possible and make
ordinary edit–build–run cycles short. Bootstrap parity alone is not the goal.
The user approved recording this agenda and starting its most ambitious idea:
**change the cost of native text through buffers, slices and builders**.

## Evidence and targets

[Phase100](../../implementation/phase100/README.md) measures complete programs,
not just kernels. Dependency planning already takes 0.33–0.36× upstream time on
selected larger graphs. Source indexing takes about 2.15×; rendering about 1.35×
on one worker and accelerates about 2× on four cores. Our emitted C is about
3–3.5× larger and takes Clang about 2–3.5× longer to build. These are distinct
applications and clocks, not a universal compiler ratio.

The installed native compiler is Phase98; Phase99's faster self-compiling image
is still experimental. Keep those identities separate throughout this work.

| Priority | Ambitious change | Conditional gain estimate | Complexity |
| --- | --- | --- | --- |
| 1 | Native text: compact immutable storage, cheap slices, builders and efficient joins | 2–5× text-heavy work; perhaps 1.5–3× complete rendering | High |
| 2 | Whole-function typed native lowering: unboxed loop state, borrowed read-only parameters, direct known calls | 1.5–3× applicable record/ownership/dispatch-heavy programs | High |
| 3 | Smaller emitted C and incremental native compilation | 3–10× warm builds; 1.5–3× clean builds | Medium–high |
| 4 | Fuse producers and consumers; eliminate intermediate lists/records/text | 1.5–4× applicable pipelines | Medium–high |
| 5 | Parallel construction/output with sensible task granularity | Aim for about 3× on four physical cores versus today's roughly 2× | Medium |

These estimates are hypotheses, not measurements or promises, and must not be
multiplied together. Existing direct/scalar workers, sharing certificates and
borrowed observers are the starting point for item 2, not features to reinvent.
Replacing the dependency application's quadratic lists with an index is a
separate algorithmic improvement; do not label it a compiler optimization.

## First experiment: change native text representation

Today's linked String representation exposes allocation, traversal, rebuilding
and ownership traffic for input scanning, formatting and concatenation. The
ambitious target is for text to cost approximately its bytes plus useful
computation, rather than repeated per-character heap operations. It should help
source indexing and image output and eventually the compiler's lexer/emission.

First inspect the actual selected runtime and generated code, then obtain a short
physical profile or controlled intervention. Reuse authenticated Phase100 C,
binaries, complete inputs and independent expected outputs. Do not rebuild a
compiler merely to discover whether a runtime mechanism can work.

Prototype a general representation boundary, not an application-specific fast
path. Candidate designs include immutable contiguous code-point/UTF-8 storage,
cheap suffix views, small bounded chunks, and append builders/ropes. Choose after
checking the current Term ABI and ownership protocol. A packed representation
must still expose exactly the logical String constructors; Unicode scalar
semantics, embedded NUL, shared suffixes, retained aliases, equality, ordering,
destruction and parallel ownership all constrain the choice. Never substitute
byte indexing for character indexing silently. Keep GPU compatibility explicit;
a CPU-only exploratory prototype does not qualify a general runtime replacement.

Use small generated-C interventions to establish value, clearly labelled as
such. A successful intervention must then be generated by the compiler written
in Bend, with the runtime source and emission boundary tracked. Do not mistake
a hand-patched executable for a new self-hosted release.

## Sequential gates and fast loop

1. Record the representation hypothesis, affected ABI sites and falsifiers.
   Two bounded offline collaborators audit the representation and prepare
   independent controls; root owns the serial guarded target queue.
2. Establish a baseline from saved products; retain complete stdout, exit status,
   memory and attribution. Test one general representation change first.
3. Run Unicode/alias/append/compare/drop controls, then source-index and complete
   rendering. Preserve the graph win and exact parallel image. Alternate baseline
   and candidate with the same Clang flags and CPU affinity; reuse pinned oracles.
4. Seek substantial gains on two distinct applications and a small compiler
   request before paying for full self-compilation/release rebuilding. If only
   one class improves, report that limit and inspect why instead of claiming
   the whole agenda succeeded.
5. Only a surviving implementation advances to affected native conformance,
   existing laws, broad program checks and genuine B1/B2 qualification. Preserve
   failed attempts. Promotion is a separate evidence-based decision.

Keep measured application runtime, compiler request time, native C build time,
memory, correctness and source complexity separate. Every larger abstraction
must earn its complexity with general value. Use seconds-long replay for routine
iteration; longer validation happens after a substantive result. Guard memory,
disk and process duration; parallelize analysis, not competing timing targets.

## Following the first result

If text becomes cheap but allocation/dispatch remains, extend typed lowering
across complete functions using verified layout/ownership facts. If Clang then
dominates the user workflow, prioritize reusable runtime objects and stable
function/module products without sacrificing small-helper inlining. Fusion and
parallel builders should build on the representation rather than introduce
another competing IR. Update this agenda with measured wins and rejected paths.
