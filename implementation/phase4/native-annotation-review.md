# Independent review of native annotation partitioning

The disposable wrapper's partitioning and demand order are sound for its stated domain: successfully prepared, finite checked books and immutable shared context. This is permission to continue a bounded component experiment, not promotion into the compiler or a claim of parallel speedup. Canonical compiler modules remain unchanged.

`ap_ready` derives one context and stop list before selecting definitions. Fork2 splits the selected list in half; fork4 applies the same split within each half. Every worker receives the same original context/stops. Joining left before right preserves the exact input definition order, including duplicates, empty chunks and stopped entries. It does not rebuild a context from each chunk or carry facts across changed books. The underlying per-definition annotation remains unchanged. Fresh binder/type-analysis behavior therefore depends on the same immutable inputs rather than worker scheduling. This argument does not promise deterministic resource failures or error ordering on arbitrary malformed books; the component first checks preparation success.

Actual emitted C `8ab07ba124eb065eaa08e136c1d46de2361aa4c4f69ffebad2a2ed38819c15db` constructs two `KA_DEFS_EXCEPT` tasks with their original left/right join indices and retained context/stop roots. Its serial fallback uses the same workers. The timed path calls `AP_HASH_DEFS`, delivers a complete scalar U32 into continuation `MAIN_K9423`, and only then builds the `IO.now` action in `MAIN_C9424`. Full structural consumption is inside the clock; merely returning a lazy annotation list cannot end the interval early. Exact structural serialization/file output follows the clock, while process wall includes those operations and preparation.

The hash visits all KDef/KTerm fields, strings, child lists and removed names. A 32-bit hash is not a correctness oracle: the later complete canonical output comparison is essential. The JS oracle additionally compares full structured values against frozen B1 `annotate_selected`; its serial/fork comparisons test chunk semantics, not actual native thread execution. Native output/thread-path gates remain separate. The wait4 resource helper waits for the native process and records its thread-inclusive CPU usage/high-water RSS; neither task construction nor a thread flag alone proves concurrent work.
