# Phase84: replace native work and test the complete request

Authorization: after Phase83 investigation, the user asked us to try hard to
establish a route to upstream compilation parity. This phase implements and
tests hypotheses; it must not relabel research estimates as achieved gains.

Baseline source `7352a00`, installed Phase82 B2 `098320e8`, checked B1 `8a400725`.
The qualified three-source ratio is1.328× B2 upstream, needing24.7% less time.
The corresponding B1 ratio is1.673×. Generated-C execution, Clang time and
compiler requests remain different metrics.

## Replacement hypotheses

Three agents prepare source patches in isolated small copies. Root alone applies
patches, builds, measures, integrates and commits:

1. Couple native annotation with production of the existing erased runtime
   product. Remove separate recursive erasure/type interpretation where possible.
   Full elimination of annotated trees also requires replacing scalar/observer
   consumers; a partial fusion must be described as partial, not a completed IR.
2. Avoid work after a worker route is definitely refused, using the actual
   lowerer's routing decisions. Ordinary and product self calls differ; a raw
   syntactic non-tail-recursion heuristic is not sufficient proof. Preserve
   unknown fallbacks and final generated C.
3. Share exact-source report/world work without reconstructing books or walking
   constructor owners repeatedly. Existing safe-closure caching is retained if
   a new graph costs more. No disabling reports or weakening trust decisions.

The first hypothesis pursues general replacement; the other two investigate
distinct costs exposed by Phase83. None is assumed to reach parity alone.
No semantic compiler algorithm moves to host JavaScript.

## Fast experimental sequence

Preserve every attempt, source patch, compiler identity and failed check. Build
checked B1 using the existing equality-profile workflow and36 frontend controls.
Use a fresh source snapshot per candidate; keep the installed compiler intact.

First compare exact generated C and ordinary observations on Numeric, Map,
Functions65 and Small, with baseline/candidate roles interleaved. Each request
uses a fresh process. Explicit Base preparation and compiler imports are
separately recorded, unchanged from the established contract. Include every
new product construction and cleanup in request time.

Measure individual patches before a combined candidate. Build genuine B2 only
for a promising general candidate, then compare with the actual baseline B2 and
pinned TypeScript on the eight-source Phase83 set. Two-round screens reject
clear failures; a promotion claim needs balanced repeated samples and appropriate
conformance/selfhosting/installed checks. Exact complete C permits scoped reuse
of native execution evidence; changed C requires fresh execution comparisons.

The ambitious target is20–25% complete B2 request savings across diverse inputs.
If experiments fall short, report the actual result and architecture limits.
Do not expand a broad representation migration on a local-only win. A smaller
independently useful change may be retained only with proportionate correctness,
performance and simplicity evidence, explicitly below the parity target.

## Correctness boundaries

Preserve quantity erasure, dependent substitution, constructor identities,
layout refusals, foreign/source ordering, raw/injected API behavior and trusted
owned permissions. Success-C identity alone does not establish error behavior:
include rejected branches, product fallback, recursion, arrays, sharing and proof
trust controls relevant to each change. Runtime optimizations must not silently
disappear to improve compilation speed.
