# Erasure product: neutral, rejected for integration

Root completed the proposed finite controls and native medium frontend screen.
The prototype remains preserved as an experiment; it is not selected for
maintained integration, and no further iteration is proposed in this campaign.

The [complete-value receipt](../../../build/phase178/erasure-values01/report.json)
passes all 1,474 observations. These compare complete values, ordered reference
occurrences, compatibility APIs, retained aliases, closure products and
incremental results. They support the bounded semantic change; they are not a
general equivalence proof.

The [native request screen](../../../build/phase178/front-product-medium01/result/report.json)
uses the same 656,302-byte source in B/C/C/B order:

| Run | Complete frontend seconds |
| --- | ---: |
| Baseline 1 | 12.234 |
| Candidate 1 | 12.312 |
| Candidate 2 | 12.131 |
| Baseline 2 | 12.234 |

Reported frontend medians are 12.234 versus 12.2215 seconds, ratio 0.998978.
Whole-process medians are 14.81627 versus 14.78840 seconds, ratio 0.998119.
All four outputs match. This is a neutral screen, not evidence of a useful
speed improvement, a full-build result, or a confidence interval.

The producer genuinely removes the immediate erased-body reference traversal
for ordinary definitions, and body-only compatibility calls suppress reference
collection. Nevertheless, the complete measured computation is neutral. The
experiment does not separately attribute the cost of product returns,
continuations, collection or destruction, so it cannot establish which cost
offset the removed traversal. Preserve the implementation and receipts instead
of promoting source-level work removal as an elapsed-time win.

The author only inspected root's existing receipts to write this note. No new
compiler, benchmark or generated-program execution was performed.
