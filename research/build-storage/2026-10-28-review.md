# Review of the proposed old-build deletion

Read-only review at `8bd91d2`, 2026-10-28. No build files deleted, no compiler
targets executed. The proposed command is **not safe to run unchanged**. Its
inventory is a useful starting point, and substantial old bulk is likely
retirable after an artifact-level review.

The [original proposal snapshot](deletion-proposal-2026-10-28.txt) is preserved
for review; its deletion command is not endorsed by this assessment.

## Measured storage

The [metadata inventory](proposal-inventory-2026-10-28.json) pins the supplied
`deletion_proposal.txt` and records the method. The preserved
[script](inventory-2026-10-28.py) performs only a metadata walk, not full-content
hashing or deletion. It is the preserved one-off method: reproduction must use
a fresh output path; it refuses to overwrite the original inventory.
It observed 1,657,648 regular file paths, 1,623,999 unique
regular-file inodes, across156 top-level build directories in57.73s, with no
stat errors. It does not traverse symlinks.

| Observation | Size |

| `selfhost/build`, `du` including directory metadata | 64.06 GiB |
| Unique regular-file allocated blocks | 62.85 GiB |
| Whole `/home/ai/bend2` workspace | 76.97 GiB |

The29.61 GiB figure is **before safety exclusions**, not approved recovery. It
excludes directory metadata, open-file retention and concurrent changes. The
roughly1.8 TiB shared filesystem had only about3.1 GiB available, but most of its usage
is outside this77 GiB workspace. Local retention helps; it cannot alone prevent
other writers exhausting the mount.

The proposed directories contain1,268,390 regular file paths. Thus this is also
a **file-count problem**, not just a few large textual QBE products. Small reports
and logs should be packed by closed experiment, rather than kept indefinitely
as millions of loose files. The roughly1.2 GiB difference between separate `du`
and regular-file snapshots includes directory metadata and other excluded entries;
it is not a separately measured recoverable amount.

## Specific problems with the proposal

1. **A live lock is in the deletion set.** The current
   [shared supervisor](../../selfhost/tools/performance/programs/support.py#L54)
   uses `selfhost/build/phase32/execution.lock`. The current
   [Phase111 guard](../../selfhost/tools/performance/phase111/guard.py#L11)
   imports this module. Unlinking a held lock permits a new lock inode at the
   same path, potentially admitting simultaneous jobs. Phase32's age says
   nothing about this current operational role.
2. **Toolchain reacquisition has a transitive dependency.** Current Phase144
   `programs/runtime-v04.py` and Phase137 `loop/build-v01.py` use Phase123's
   aligned builder, which executes the Phase108 QBE tool. Its
   [setup script](../../selfhost/tools/performance/phase108/toolchain/setup.sh#L8)
   requires and copies `build/phase107/toolchain/qbe-1.3`. The proposal removes
   Phase107. This breaks the existing reacquisition procedure; it does not imply
   that the already-built Phase108 executable stops running.
3. **Uncommitted work is excluded by the scan.** The working tree contains
   modified Phase6/68 reports and untracked tools for those phases. Examples are
   `selfhost/tools/performance/phase6/membership-counts.mjs` and
   `phase68/controls/product-layout-v3.mjs`; both consume build-attempt inputs.
   Preserve these roots until their owner confirms closure. Their files are
   outside this review's edits.
4. **Evidence capsules do not imply restorable binaries.** The
   [Phase146 archiver](../../selfhost/tools/performance/phase146/archive-v01.py#L65)
   deliberately excludes SSA, assembly, objects, large APIs and ELF files. It
   retains identities and paths, not those bytes. Source can reproduce behavior
   without reproducing the exact ELF needed to symbolize a historical profile.
5. **Direct phase references are an imperfect retention boundary.** They miss
   shared methods, setup prerequisites, generated path names, receipt-driven
   inputs and non-current-phase tools. Conversely, keeping all of Phase111
   because some files are used retains about9 GiB of mostly unrelated work.
   Preserve the required artifact closure, not all or none of a phase.

A bounded independent audit checked Phase146/144/137 candidate roots,350
transitive JSON receipts and the actual installed native Phase102 B2 admission.
It found no additional proposed-deletion artifact dependencies in that sample.
This does not prove there are none, and we do not claim the current compiler
executable itself necessarily breaks when the entire proposal is removed.

## Existing mechanisms and failure mode

The current guard admits a default job with only416 MiB free, before taking the
shared execution lock; it has no whole-campaign disk reservation or continuous
free-disk check. Per-file limits do not bound all files created by a run.

Existing exact archive-member deletion and immutable hardlink workflows are
usable foundations: [Phase146 audit](../phase146/validation-and-storage.md),
[Phase131 deduplication](../phase131/storage.md). Their recorded recovery has
already happened; do not count it again. Previous evidence packaging, journals
and verified restoration are more useful than another broad `rm -rf` heuristic.

## Recommendation

Adopt the proposed [retention policy](../../docs/self_hosted/build-retention.md):
named installed/qualified/fallback/active roots, typed dependency edges, permanent
compact scientific evidence, explicit exact-profile bundles, closed-run artifact
cleanup, and whole-run disk admission with a reserve. No policy enforcement or
deletion is enabled by these documents.

First aim to recover5–10 GiB from a reviewed file list, rather than deleting all94
directories. Exclude the concrete lock/setup/unfinished-work dependencies above,
pack unique small evidence and source, and audit actual archived members before
removing unique bulk. Then introduce a versioned disk-aware guard and close-run
retention manifest. A simple inventory/planner is sufficient; a new general
compiler cache is unnecessary for this job.
