HOW CANDIDATES WERE CHOSEN
--------------------------
Modification dates are useless here: 88 folders were all touched on
2026-10-23 (a mass rebuild), so everything looks recent. Instead:

1. Collected every "build/phaseN" path referenced in tracked files belonging to
   current work:
     implementation/phase13x-14x/**, selfhost/tools/performance/phase13x-14x/**,
     selfhost/tools/*.mjs, selfhost/tools/*.sh, selfhost/*.mjs
   (git grep with :(glob) pathspecs, so * does not cross directories)
2. Phases < 130 referenced there are KEPT:
     2 66 82 83 86 88 89 90 91 92 93 94 97 98 99 100 101 102 105 108
     111 112 113 114 117 118 124 125 126 127 128 129
   (phase111 alone has ~48k references and is 9.5 GB; it stays.)
3. Every other selfhost/build/phaseN with N < 130 is a candidate.

CAVEATS - PLEASE CHECK BEFORE DELETING
--------------------------------------
- Each old phase's OWN scripts/evidence (implementation/phaseN/,
  selfhost/tools/performance/phaseN/) still read its build folder.
  Re-running those historical scripts would fail after deletion.
- Several tools import modules directly from build folders and assert exact
  SHA-256 hashes (e.g. selfhost/tools/performance/phase12/
  call-broad-noseed-prepare.mjs). A rebuild may not reproduce byte-identical
  artifacts, so treat deletion as NOT reliably reversible for those checks.
- The reference scan only covered tracked files. Untracked notes, the
  bend2/ parent checkout, or agent memory might reference these paths.
- Dynamic paths (e.g. `build/phase${n}`) would not be caught by the scan.
- If recorded evidence in git (results, RESULTS.md, evidence/) is all you need
  from old phases, deletion should be safe.
