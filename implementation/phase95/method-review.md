# Offline method and integration review

Reviewed the frozen `selfhost/tools/performance/phase95/compiler-compare.py`,
`membership-run-v2.py`, `membership-measure02/report.json`, frozen03 sources and
the two membership build03 receipts. No targets or compiler builds were run for
this review. The initial review preceded the compiler comparisons; the final
offline update checked all 95 emitted-C identities and their retained raw logs:
48 screen, two full-input and 45 broad products, each matching its named oracle.

The six-source geometric ratios independently recompute to 0.9966423519 for
request time and 0.9999518397 for process wall. The full D04 pair is
138,029 ms → 136,418 ms (0.9883285397), with exact output and the expected unsafe
diagnostic on both sides. These small observations support the decision **not to
promote**. No reverse-order full-input follow-up, new B2, canonical edit or release
cycle is warranted for this concluded pilot. The integration route below remains
prospective only.

The compiler method authenticates Phase92 B1, replays exactly one source change,
binds the checked candidate acquisition and its actual Clang O2 build, and changes
only the executable in the otherwise identical request command. Four alternating
rounds on six sources preserve every full C output and separate request time from
process time. The 45-case mode is an exact-product continuity gate. Self mode is
one baseline/candidate pair compiling the unchanged D04 source; it also compares
the complete expected 3,987-definition unsafe proof-refusal diagnostic. It is not
candidate-own-source checking or native B2 qualification. A material self timing
gain should receive a reversed-order confirmation before an installed-speed
claim; the frozen self mode explicitly records only one pair.

Complete request C can remain byte-identical: both membership implementations
return the same Bool for finite, well-formed string lists, and their callers use
that Bool without observing traversal order. The change avoids traversing the
tail after a hit and changes ownership work and evaluation order. This reasoning
does not establish behavior on malformed unsafe values, whole-compiler soundness,
or a checked generic equivalence theorem. The existing semantic controls include
head/middle/tail/miss, duplicates, empty strings, Unicode, prefix distinctions and
retained shared inputs.

The helper comparison's independent repetition calibration is appropriate for its
large speed differences. All 36 measured batches exceed the 200 ms floor (minimum
237 ms); three alternating rounds and first-case doubled counts are recorded.
The doubled-count ratios are 1.954 and 1.916. Timing includes the loop, checksum
printing and final shared-root release, while construction is outside. Counts
differ by role, so this is normalized throughput for the stated workload, not
equal-work process latency. Include the observed miss/tail regressions (1.059× /
1.027×), alongside the selected-hit gains. The emitted C retains per-iteration
kernel dispatch and a checksum continuation; the scaling control covers the first
case only. No new machine-code proof for every workload is asserted.

One provenance limitation is local to the helper runner: it binds acquisition C
and executable bytes but does not itself bind or validate the Clang build
receipts. The preserved `membership-baseline-build03` and
`membership-candidate-build03` receipts show successful matching Clang O3 commands
against the correct source/output paths. Include both complete receipt trees in
the final evidence binding; leave the measured method unchanged. The new
`collect.py` does bind and verify these build receipts/inputs and records their
commands. Its raw archive includes every Phase95 build-tree file and verifies
every member by readback. Collection had not yet run at this review update;
archive success is therefore not claimed here.
