# Phase90 Clang memory diagnosis (offline)

The two suggested memory flags are already enabled. The exact Clang 22.1.4 driver dry run includes `-clear-ast-before-backend`; `memory-method-inspection.json` retains that command and output. LLVM 22.1.4 initializes `-eagerly-invalidate-analyses` to true and forwards it to pipeline adaptors. The exact Lean build commit source could not be fetched, so the latter is a tagged-source finding, not a direct dump of this executable's option value. [LLVM pipeline source](https://raw.githubusercontent.com/llvm/llvm-project/llvmorg-22.1.4/llvm/lib/Passes/PassBuilderPipelines.cpp).

Eager invalidation is not a new optimization opportunity here. Its documented purpose is to trade recomputation for lower analysis retention, and even code generation can change when analyses are recomputed. Do not promise identical machine code from such an option. [LLVM tuning contract](https://raw.githubusercontent.com/llvm/llvm-project/llvmorg-22.1.4/llvm/include/llvm/Passes/PassBuilder.h).

The completed `-O1 -fno-inline-functions` attempt still hit the 6 GiB guard, much like ordinary O1. It therefore did not solve this memory barrier. The flag does not disable explicit `always_inline`. Offline lexical counts in `inlining-shape.json` cannot identify the peak pass or predict expanded IR memory. Likewise2.17× source size is a capacity-planning heuristic, not a measured memory attribution.

The parent will run plain O1 with a 10 GiB tree-RSS cap, 16 GiB available-memory requirement, a 420 s deadline and pass tracing; no already-enabled flags will be added. The next useful result is that bounded build. A completed trace can distinguish frontend/IR optimization/codegen; trace durations alone do not identify each phase's memory peak. Correlate phase intervals with the guard's sampled RSS. `-ftime-report` and `-ftime-trace` are generally finalized at completion, so a guard termination can leave no usable report.

If that attempt is killed, prefer one bounded live pass diagnostic before another flag change. `-Xclang -fdebug-pass-manager` is supported. Drain stderr continuously while retaining only timestamped last-pass/RSS snapshots, a small head/tail and counts; avoid storing unrestricted per-function output. This locates the last active pipeline region but is instrumented diagnostic evidence, not a performance comparison. It also does not prove that the last pass allocated all retained memory.

No standalone matching `opt` or `llc` was found in the checked executable locations. Clang could still split frontend bitcode emission from optimizer/codegen using `-emit-llvm -c -Xclang -disable-llvm-passes`, then a second Clang invocation on bitcode. This costs additional disk and rereading: only 415 MiB was free during inspection, so do not start that split without reserving bounded artifact space. The exact C cdecl O0 image is already a correctness fallback; an optimized build still needs all independent gates.
