# Final native compilation latency and the remaining compiler tax

Final compiler03's clean source-to-C request time is **3.41827× upstream
for checked B1** and **2.16517× for genuine B2**, as an equal-family geomean over
Numeric, Array and Lexer. A separate contemporaneous Numeric comparison finds
that the final release costs **6.54% more B1 request time** than Phase69's
release. B2's corresponding point estimate is **1.09% more**. The runtime gains
therefore come with a measurable B1 compilation cost on this workload; this
phase does not establish native compilation-speed parity.

These numbers measure **Bend source loading/checking and C generation by the
compiler**, compared with Bend's pinned upstream compiler implemented in
TypeScript. They do not measure Clang, the runtime of emitted C programs,
JavaScript-target compilation, or compiler bootstrap/image generation. The
[generated-program runtime results](native-runtime-results.md) report the
separate execution metric. B1 is the checked upstream-bootstrapped compiler;
B2 is the compiler generated by that B1 and qualified against it.

## What is inside each clock

The timed Bend operation is the ordinary checked native request through
`D.inspect(source, {mode:'native', withReport:true})`. It includes request-time
source/import processing, type checking, annotation and complete C emission.
The process first imports its compiler and uses an explicitly prepared Base;
imports and Base preparation are outside the request clock. A request must not
change the prepared cache. There is no persistent warm compiler process across
samples and no benchmark-only unchecked route.

The upstream operation loads/checks the source and Base, validates the book,
then calls its normal C compiler. Upstream's Base work remains inside its
request clock; Bend's explicit Base preparation is reported separately. This
is the declared prepared-Base comparison, not an equal cold-start total or a
claim that the two frontends cache exactly the same work.

B1's explicit Base preparation took **3488.06ms**; B2's took **3049.62ms** in
this campaign. Median request-process imports were about **59ms B1**, **108ms
B2**, and **220–236ms upstream**, depending on source. These values must not be
silently included in, or subtracted from, the reported request ratios. The
benchmark also excludes Clang compilation and emitted-program execution.
Instrumentation and CPU profiles belong to separate diagnostic plans; none of
these clean samples run the profiler or stage wrappers.

## Same-campaign comparison with the prior release

Historical Phase69 reported **3.23121× B1** and **2.18266× B2** upstream on the
three-source native request set. Comparing those numbers directly with this
phase's ratios would mix campaigns and host timing conditions. The
[retained native timing audit](native-runtime-noise-audit.md) already shows
large drift for some identical saved executables. A ratio change alone is
therefore insufficient evidence of a release regression or improvement.

To measure the actual release difference, a separate small screen alternated
**Phase69 B1, final03 B1, Phase69 B2 and final03 B2** on Numeric. Four complete
rotations place each role in every position once. Each role uses its actual
checked/genuine image and a fresh private prepared Base. There are **four
preparations and sixteen full checked requests**. The old and new releases
have different C output; each must exactly reproduce its own independently
native-validated program. Thus this measures the cost of the whole releases,
including their different optimization work, rather than attributing a change
to one pass.

| Stage | Phase69 median, ms | Final03 median, ms | Final/old median | Final slower paired rounds | Geomean paired ratio |
| --- | ---: | ---: | ---: | ---: | ---: |
| B1 | 2270.208 | 2418.677 | 1.06540× | 4/4 | 1.08465× |
| B2 | 1525.745 | 1542.316 | 1.01086× | 3/4 | 1.00741× |

B1 is slower in all four paired rounds, and even its fastest final sample is
slower than the slowest old sample. That supports a real compiler cost on
Numeric: **6.54% by the median ratio**. The paired-ratio geomean is **8.46%
more time**, partly reflecting the retained 2639ms final sample. Both
summaries are disclosed; neither is selected to disguise the unfavorable
result.

B2 is slower in three of four paired rounds. Its median ratio is **1.09% more
time**, while the paired-ratio geomean is **0.74% more**. The old B2 samples
span both sides of the new ones, so this smaller effect deserves a more cautious
interpretation. Four rounds on one source establish a bounded screen, not a
precise universal tax, a confidence interval or a result for all programs.

## What was kept and rejected

The [factorial screen](compiler-factorial.md) separately tested the occurrence
update and an ordinary-ready observer-analysis skip on edited diagnostic
images. All 32 requests reproduced the same Numeric C, but the occurrence
update slowed B2 in all four paired rounds and failed the predeclared retention
rule. Final compiler03 removes the ten added lines and restores the existing
`index_set` update. The observer skip did not show consistent benefit and was
not applied. Diagnostic image timings were not substituted into final checked
compiler results.

Earlier lazy product-demand and compact-body work, general observer emission
and checked Bool admission remain in the selected release. This final
comparison does not independently assign a percentage gain or loss to each
pass. Profiles identify possible work to investigate; their overlapping sample
families are not additive, and skipping a sampled function does not guarantee
that all its apparent time disappears from a real request.

For generated-program behavior, checked compiler03 B1 and genuine B2 each
reproduced all **twelve** compiler02 programs in full: **24/24 exact C
emissions**. The qualification also established equality of all 56 frozen host,
runtime and effect-support files, Base and the original acquisition support.
Consequently those prior program-runtime measurements can be carried forward
through explicit code identity; they are not relabeled as fresh runtime
measurements from compiler03. Compiler-request latency received its own fresh
measurements precisely because unchanged output does not imply unchanged
compiler cost.

small compilation set. Program-runtime improvements and self-hosting
correctness do not erase that remaining metric. Further compiler work should
start from the retained profiles and a short contemporaneous control, while
preserving runtime code quality and avoiding another unmeasured complexity
increase. No additional optimization or target run was performed after these
results.
