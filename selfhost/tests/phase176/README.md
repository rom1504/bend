# Calibrated native frontend screens

Use this small runner to dispatch independent **prebuilt frontend** comparisons
in software. Compiler algorithms remain in Bend. Python handles processes,
identity checks and measurements; Bun hosts independently checked value oracles.

Two workers use different physical cores (3,5 on this host). Four workers use
0,1,2,3, avoiding SMT siblings. Supply CPUs explicitly after inspecting the host.
One aggregate guard owns the execution lock, RSS, disk and deadline; do not nest
per-job guards. Final comparisons use one worker on CPU3.

```sh
python3 -B selfhost/tests/phase176/job.py --cpu 3,5 screen-FRESH 120 8 \
  python3 -B selfhost/tests/phase176/batch.py \
  --manifest experiments/phase176/calibration-small.json \
  --cpus 3,5 --out selfhost/build/phase176/screen-FRESH
```

The manifest pins its images, source inputs and timing adapter. Each independent
job keeps baseline/candidate pairs on the same CPU and reverses order next round.
`{out}` is replaced with that job's fresh result directory. Keep the results and
failures. Use `calibration-medium.json` for the larger two-candidate scaling step.
Budgets must include other writes to this shared filesystem; retain the 5GiB
reserve. Close receipts are generated by `job.py`.

The supported payloads are deliberately restricted to
`phase175/native-frontend.py`, checked `hosted.mjs acquire`, and fixed supervisor
controls. They do not detach descendants. **Do not put native.py or other tools
that create new child sessions inside this batch.** Run those directly under
the outer guard. Child creation stays on the main OS thread so the existing
guard sees the process tree. Deadline, ordinary failure, continued independent
work and changed-input refusal are checked by `batch-controls.py`.

Interpret parallel results as screening and throughput, not final speed claims.
Small proxies recover the known broad positive/neutral outcomes here, but do not
reliably predict gain magnitude. Differences of a few percent need repeats or a
larger input. No automatic acceptance policy is implemented. The old indexed-store
regression has a different interface and is not part of this calibration.

## Trying a source change

`prepare.py` reuses the retained metadata-only extractor, bound explicitly to
Phase175's maintained source. It checks named overrides and protected declarations.
`--snapshot-parser` instead binds the exact earlier parser source and declaration
order, allowing a matched comparison with its prebuilt native image. Use the
same installed Phase171 producer for that historical comparison. These are
experimental closures, never a fabricated self-hosting stage.

1. Source-check a small closure with the pinned upstream compiler.
2. Compare complete values, independent literal expectations and retained aliases.
3. Build the small native workload and inspect actual private workers.
4. Run `native-screen.py` on isolated CPU3, with the upstream-checked expected
   output. Its process time includes input construction, digest and destruction.
5. Transfer a survivor to native parsing of real compiler sources, then the full
   frozen input. Reserve complete compiler acquisition/qualification for useful
   complete-component gains.

`pattern-machine.bend` preserves the rejected mutually recursive work machine.
`pattern-single.bend` is the separate single-loop experiment. Neither is selected
in the maintained compiler. `pattern-controls.mjs` compares all value fields;
hashes in native workloads supplement these checks and are not correctness proofs.
Forward `law` signatures are types, not mathematical equivalence proofs.

Reproduction commands and exact observations are in the
[Phase176 report](../../../implementation/phase176/README.md). Historical APIs can
retain now-stale manifest identities: reacquire a checked API against the current
manifest instead of modifying its old receipt or weakening input verification.
